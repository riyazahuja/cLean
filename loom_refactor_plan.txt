```lean
def saxpyProgram : KernelEnv := ...

theorem saxpy_correct
```

**What Exists**
The actual verification stack is standard WP/Hoare-style verification.

At the bottom, assertions are separation-logic assertions over states and resources:

```lean
CSL.Assertion = State → Resource → Prop
```

A kernel spec is valid when four things hold, in [CFG.lean](/data/user_data/riyaza/cLean/CLean/WP/CFG.lean:1876):

```lean
pre init resource
pre ⊢ invariant
StepPreserves invariant
Finalizes invariant post
```

Then [KernelSpec.partial_correct](/data/user_data/riyaza/cLean/CLean/WP/CFG.lean:2383) says: if the spec is valid and execution terminates, the postcondition holds.

So mathematically:

```text
pre(init) ∧ Valid(spec) ∧ init ⇝* final ∧ final cannot step
-----------------------------------------------------------
post(final)
```

That part is clean.

**Where The Complexity Comes From**
For straight-line code, the WP is exactly the usual recursive WP. See [wpInstrList](/data/user_data/riyaza/cLean/CLean/WP/Block.lean:11):

```lean
wpInstrList [] post = post
wpInstrList (i :: rest) post = wpInstr i (wpInstrList rest post)
```

So yes: “unfold the program backwards, compute/prove the minimal precondition, then prove the real initial precondition entails it” is exactly the intended theory.

But the current examples expose the raw ingredients needed to prove that entailment:

- memory bytes for each load/store
- `DecodedScalar` and `EncodedScalar`
- address-resolution facts
- byte-range disjointness
- register ownership
- scheduler/single-warp control
- loop/block invariants
- per-lane resources

Those are not the final mathematical API. They are the backend facts that a nicer `SaxpyPre` or `ArrayS32` abstraction should hide.

SAXPY shows this clearly. The clean postcondition exists as [saxpyPost](/data/user_data/riyaza/cLean/CLean/Examples/Saxpy.lean:2321):

```lean
∀ i, i < params.n →
  readGlobalS32? st (saxpyLaneOutputOffset params i) =
    some (saxpyExpectedValue params (xs i) (ys i))
```

But [saxpy_vector_partial_correct](/data/user_data/riyaza/cLean/CLean/Examples/Saxpy.lean:2569) still takes `SaxpyVectorProofs`, which is basically a bundle saying “for every lane, all the byte/register/address/resource facts needed by the scalar WP proof hold.” That is why it feels too complicated.

The next abstraction should be:

```lean
SaxpyConcretePre init params xs ys oldZ
  ⊢ facts needed by SaxpyVectorProofs
```

Then the final theorem stops mentioning `SaxpyVectorProofs`.

**How Loops Work**
Loops require user-supplied invariants. That is not accidental; it is the normal deductive-verification story.

For acyclic code, WP can just recurse backwards. For loops, the true weakest precondition is a fixed point. In practice, Hoare/WP systems ask for an invariant and then prove it is preserved.

In this repo, the invariant is:

```lean
InvariantMap := BlockLabel → CSL.Assertion
```

So every CFG block label gets an assertion. In [Loop.lean](/data/user_data/riyaza/cLean/CLean/Examples/Loop.lean:355), for example:

```lean
loop:
  ∃ i p, i ≤ n ∧ pc = loop ∧ acc = sum(0..i)
body:
  ∃ i, i < n ∧ pc = body ∧ acc = sum(0..i)
exit:
  pc = exit ∧ i = n ∧ acc = sum(0..n)
```

The block VC shape is [blockVC'](/data/user_data/riyaza/cLean/CLean/WP/CFG.lean:244):

```lean
invariants label ⊢ wpInstrs body termPre
TerminatorVC ... termPre
```

For `br loop`, you prove the backedge re-establishes `invariants "loop"`.

For `cbr`, [TerminatorVC.cbr](/data/user_data/riyaza/cLean/CLean/WP/CFG.lean:224) splits the proof:

```text
termPre entails truePre OR falsePre
truePre  proves branch-to-true-target invariant
falsePre proves branch-to-false-target invariant
```

That is the branch-sensitive fix. Without it, a conditional branch would have to prove both target invariants at once, which is too strong for real loops.

**Design Audit**
The theory is sound and basically the right one: small-step semantics, separation-logic assertions, instruction WP rules, CFG invariants, and partial-correctness soundness.

The current weakness is presentation. Theorems still look like internal VC proof plumbing instead of user-facing correctness theorems.

The important missing layer is a spec frontend:

- define high-level memory predicates like `GlobalArrayS32`
- define `SaxpyPre`, `MatmulPre`, etc.
- prove those imply the byte/resource/address facts
- package single-warp mode so `OnlyRunnableWarp` is not exposed
- let users provide loop invariants, but not low-level terminator VCs
- generate or normalize the block VCs from the IR

So: the implementation is doing the right verification-theory thing, but the examples are currently closer to “proof kernel acceptance tests” than the final pleasant API.

But with two caveats:

1. It is not packaged as a generic `PCM` typeclass.
2. It is not yet a full concurrent separation logic with a polished parallel/concurrency rule. It has the resource/separating/frame machinery needed for CSL, and some concurrency-oriented resource keys, but current checked proofs mostly use it in single-warp mode.

The resource algebra is in [Resource.lean](/data/user_data/riyaza/cLean/CLean/CSL/Resource.lean:121).

Carrier:

```lean
structure Resource where
  entries : List Entry
```

Unit:

```lean
def empty : Resource
```

Composition:

```lean
def compose (a b : Resource) : Resource :=
  { entries := a.entries ++ b.entries }
```

Partiality:

```lean
def canCompose (a b : Resource) : Prop :=
  ∀ ea ∈ a.entries, ∀ eb ∈ b.entries, Entry.compatible ea eb
```

So composition is implemented as a total append operation plus a definedness predicate. That is a standard way to encode a partial commutative monoid in Lean.

Commutativity is not definitional equality because list append is ordered. Instead the code has equivalence:

```lean
def Equiv (a b : Resource) : Prop :=
  ∀ entry, entry ∈ a.entries ↔ entry ∈ b.entries
```

and proves:

```lean
compose_comm_equiv :
  Equiv (compose a b) (compose b a)
```

So mathematically it is a PCM up to `Resource.Equiv`.

The compatibility model is here: [Resource.lean](/data/user_data/riyaza/cLean/CLean/CSL/Resource.lean:43).

Same-key resources are compatible only for read/read byte cells:

```lean
Cell.compatible
| .byte .read _, .byte .read _ => True
| _, _ => False
```

Different keys are always compatible. That means:

- two reads of the same byte may coexist
- writes are exclusive
- registers, predicates, tokens, fragments are exclusive
- barrier/warp/atomic/MMA-ish tokens are already represented as resource keys, even if not fully used by core examples

The separation logic layer is in [Assertion.lean](/data/user_data/riyaza/cLean/CLean/CSL/Assertion.lean:6):

```lean
abbrev Assertion := State → Resource → Prop
```

Separating conjunction is:

```lean
def sep (p q : Assertion) : Assertion :=
  fun st r =>
    ∃ r₁ r₂,
      Resource.canCompose r₁ r₂ ∧
      Resource.Equiv r (Resource.compose r₁ r₂) ∧
      p st r₁ ∧
      q st r₂
```

So `p ∗ q` literally means: split the current resource into compatible pieces, give one to `p`, one to `q`.

The WP frame rule uses this. See [wpInstr_frame](/data/user_data/riyaza/cLean/CLean/WP/Instr.lean:58):

```lean
(wpInstr ... post ∗ frame) ⊢ₛ
  wpInstr ... (post ∗ frame)
```

provided the frame is stable under the instruction step. Stability is:

```lean
StableUnder step p :=
  ∀ st st' r, step st st' → p st r → p st' r
```

So the theory is:

```text
instruction owns/updates its footprint
frame owns disjoint compatible resources
frame is stable under this step
---------------------------------------
instruction preserves post ∗ frame
```

That is exactly separation-logic framing.

Where the “concurrent” part currently stands:

The resource model is concurrency-ready: it can separate ownership of bytes, registers, predicates, lanes, barriers, warp tokens, atomics, fragments, etc. The machine semantics is also small-step and can model scheduler choice. But the checked examples avoid real multi-warp interference by proving:

```lean
StepMachineSelects inv 0 0
```

usually from:

```lean
inv ⊢ₛ OnlyRunnableWarp 0 0
```

So today it is best described as:

> a first-order-ish shallow separation logic with a PCM-style resource algebra, used for WP/frame reasoning, with concurrency-oriented resources, but currently exercised mostly as a single-warp CSL fragment.

The next real CSL step would be proving preservation under unrelated warp steps: if warp A owns its footprint and warp B steps with disjoint resources, A’s invariant remains stable. That would turn the current single-warp proof discipline into genuine multi-warp concurrent separation reasoning.


in [Resource.lean](/data/user_data/riyaza/cLean/CLean/CSL/Resource.lean:121).

```lean
| .byte .read _, .byte .read _ => True
```

So one read permission can effectively be split into two identical read permissions because `Equiv` ignores duplicate list entries. That gives contraction/shareability for reads. Writes do not have this because write/write is incompatible, so `canCompose` blocks splitting write ownership twice.

This is a reasonable simple PCM-ish model, but it is not a polished resource algebra. It is not cancellative, not quotient-packaged, and not a precise fractional permission model. If later we need serious permission accounting, I would replace this with either:

```text
ResourceKey → Share × CellShape
```

or a quotiented finite map/multiset with an explicit share algebra.

**Single-Warp Mode**
The operational semantics has CTAs, warps, and lanes.

Types:

```lean
CTAId  := Nat
WarpId := Nat
LaneId := Fin 32
```

State hierarchy:

```text
State
  ctas : CTAId ↦ CTAState
    warps : WarpId ↦ WarpState
      lanes : Array LaneState  -- 32 lanes
```

A lane is basically one SIMD lane/thread state: registers, predicates, local memory, PC, and status. A CUDA-style logical thread is represented by `(cta, warp, lane)`. `tid.x` is computed from:

```lean
warp * 32 + lane.val
```

then projected through `blockDim`.

The small-step semantics is machine-level nondeterministic over CTA and warp:

```lean
StepMachine.mk :
  StepWarp st cta warp st' →
  StepMachine st st'
```

So in principle any runnable warp in any CTA can step.

But the checked proofs usually prove preservation only for one selected warp, normally `(0, 0)`. This is encoded by:

```lean
StepMachineSelects inv 0 0
```

meaning:

```lean
if inv holds and StepMachine st st',
then that machine step is StepWarp st 0 0 st'
```

Most examples discharge that through:

```lean
inv ⊢ₛ OnlyRunnableWarp 0 0
```

So “single-warp mode” means the invariant rules out any machine step except CTA 0, warp 0. We are not yet proving that unrelated warps can step while preserving this warp’s invariant.

**Lanes vs Warps**
A warp step executes one instruction/terminator for participating lanes.

The control assertion:

```lean
warpAt cta warp pc lanes
```

means: the warp exists, runnable lanes are lockstep at `pc`, and the lanes participating in the current unguarded instruction are exactly `lanes`.

Instruction execution computes participants from runnable lanes and guard predicates, then applies the instruction to each participant lane. For ordinary register ops and loads this is `applyToLaneIds?`; stores are sequentialized in participant lane order. Then runnable PCs advance.

So:

- lane state is per-thread state
- warp state enforces lockstep execution for runnable lanes
- CTA state holds warps and shared memory
- IR `Block` means CFG basic block, not CUDA CTA block

Current examples mostly use:

- CTA `0`
- warp `0`
- one lane for loop/matmul scalar examples
- multiple lanes only in the SAXPY vector lift, still within one warp and `n ≤ 32`

So the semantics is multi-CTA/multi-warp capable structurally, but the proof layer currently uses a single selected warp discipline.

- the program
- the precondition
- loop invariants
- the postcondition

They should not manually assemble `blockVC'`, `TerminatorVC`, branch-control facts, and frame permutations.

```lean
KernelVCsFor env invariants post
```

with helper tactics or structured constructors that generate one obligation per block. Loops still need user invariants. That is normal. But the user should not have to touch raw terminator internals unless debugging.

I would introduce a proper resource algebra interface:

```lean
class ResourceAlgebra where
  valid : R → Prop
  compose : R → R → R
  compatible : R → R → Prop
  equiv : R → R → Prop
```

Then instantiate it with the current model or a finite-map/share model. For PTX, we will likely want read-sharing, write exclusivity, barrier tokens, atomic permissions, warp tokens, and fragments modeled explicitly.

**Priority 5: True Multi-Warp Preservation**
A fully-featured verifier cannot keep assuming only warp `(0,0)` steps.

The real theorem should say: if the scheduler steps some other warp, my invariant is preserved by separation/framing. That means proving “unrelated warp stability” lemmas:

```lean
warpInv cta warp ∗ otherWarpInv cta' warp'
```

and if `(cta, warp) ≠ (cta', warp')`, a step of one does not break the other except through shared/global resources it owns.

This is where the CSL story becomes real concurrency, not just a sequential WP with resource framing.

**Priority 6: Generalize Examples**
After the public spec layer exists, revisit examples:

- SAXPY: clean final theorem over arrays.
- Global sum: parametric `n`, not fixed `n = 3`.
- Matmul: parametric inner loop, then eventually full grid-level matrix theorem.
- Add lowered PTX/parser path so correctness is about a parsed/lowered kernel, not only hand-written IR.

**Priority 7: Then Add Hard PTX Features**
Only after the above:

1. shared memory without barriers
2. barriers and CTA synchronization
3. warp collectives
4. atomics
5. MMA/fragments

Doing atomics or MMA now would build on an awkward theorem interface and weak concurrency story.

So the short version: the next best move is not “prove a harder kernel.” It is “turn the current proof substrate into a user-facing verification API.” Once SAXPY/global-sum/matmul have clean correctness statements, then expand the PTX feature surface.

Yes: Loom can support CSL **as the assertion domain**, but Loom does not itself provide a separation-logic/resource-algebra framework.

The split is:

```text
Loom:
  generic monadic WP / VC-generation machinery over an assertion lattice l

  the assertion lattice l should be CSL assertions
  the CSL assertions are built from a PTX resource algebra / PCM
```

**Why CSL/PCM?**
PTX is not like Velvet’s simple imperative source language. Velvet mostly reasons about Lean values, arrays, and structured mutable variables. Its assertions are essentially ordinary propositions over program values/state. It does not need ownership to say “this thread owns register `%r1`,” “this warp owns these lane predicates,” “this byte is writable,” or “this shared-memory invariant is protected by a barrier token.”

PTX needs that because we eventually need to reason locally about a concurrent machine:

```text
global memory byte 0x100 is writable
∗ lane 3 owns register %r4
∗ warp 0 owns PC/lockstep facts
∗ CTA 0 owns shared-memory fragment
∗ barrier token / atomic token / MMA fragment
```

The PCM is the algebra of those resources. Mathematically, it gives us a partial composition operation:

```text
r₁ ⋅ r₂ = r
```

defined only when resources are compatible. For example:

```text
write byte a ⋅ write byte a      undefined
write byte a ⋅ read byte a       undefined
read byte a ⋅ read byte a        maybe defined, depending on permission model
reg lane0 %x ⋅ reg lane1 %x      defined
reg lane0 %x ⋅ reg lane0 %x      undefined
```

Then separation logic defines:

```lean
P ∗ Q := fun st r =>
  ∃ r₁ r₂, r₁ ⋅ r₂ = r ∧ P st r₁ ∧ Q st r₂
```

Current CLean has a first version of this in [Assertion.lean](/data/user_data/riyaza/cLean/CLean/CSL/Assertion.lean:6) and [Resource.lean](/data/user_data/riyaza/cLean/CLean/CSL/Resource.lean:121), but it is not yet the robust algebra I’d want to build on long-term.

**Does Loom Support This?**
Loom supports arbitrary assertion lattices. Its core abstraction is `MAlgOrdered`, where a monadic computation is interpreted into some complete lattice `l`; see [Defs.lean](/data/user_data/riyaza/cLean/.loom/Loom/MonadAlgebras/Defs.lean:72). `WPGen` then proves generated VCs sound by showing:

```lean
get post ≤ wp x post
```

see [Gen.lean](/data/user_data/riyaza/cLean/.loom/Loom/MonadAlgebras/WP/Gen.lean:108).

So we can set:

```lean
l := CSL.Assertion
-- morally:
CSL.Assertion := State → Resource → Prop
```

and instantiate the complete lattice pointwise:

```text
P ≤ Q      := ∀ st r, P st r → Q st r
P ⊓ Q      := fun st r => P st r ∧ Q st r
P ⊔ Q      := fun st r => P st r ∨ Q st r
⊤          := fun _ _ => True
⊥          := fun _ _ => False
```

But `∗` is **not** Loom’s lattice conjunction. It is extra BI/separation structure we add on top. Loom does not know anything about `∗`, frame rules, ownership, or PCMs unless we encode and prove those ourselves.

**Important Difference From Velvet**
Velvet’s proof world is roughly:

```text
pre : Prop
post : result → Prop
```

or for stateful programs, functions into `Prop`.

CLean/PTX’s proof world should be:

```text
pre : State → Resource → Prop
post : State → Resource → Prop
```

Velvet proves facts about values after structured code runs. PTX verification must also prove that the proof owns the right resources, frames unrelated resources, and survives arbitrary interleavings.

So the VC theorem shape is not just ordinary Hoare logic. It is separation-aware Hoare/WP logic:

```text
{P} instr {Q}
---------------- frame rule
{P ∗ R} instr {Q ∗ R}
```

provided `instr` cannot disturb `R`.

**What Governs The VCGen?**
Mathematically, the VCGen should be governed by three layers:

1. Dijkstra/WP semantics:

```text
wp (c >>= f) Q = wp c (fun x => wp (f x) Q)
```

This is Loom’s part.

2. Separation algebra / BI:

```text
emp ∗ P ⊣⊢ P
P ∗ Q ⊣⊢ Q ∗ P
(P ∗ Q) ∗ R ⊣⊢ P ∗ (Q ∗ R)
```

This is our PCM/CSL part.

3. Local-action/frame-preservation rules:

For an instruction step:

```text
wp instr Q st r :=
  ∀ st', StepInstr st instr st' →
    ∃ r', ResourceUpdate instr st st' r r' ∧ Q st' r'
```

Then the frame theorem says:

```text
(wp instr Q ∗ R) ⊢ wp instr (Q ∗ R)
```

when `R` is stable under the instruction step.

For scheduler nondeterminism:

```text
wp machineStep Q =
  intersection over every runnable cta/warp of wp (warpStep cta warp) Q
```

That is where the single-warp assumption should disappear. The scheduler is demonic nondeterminism: every runnable warp choice must preserve the global invariant.

**How To Encode Robustly**
I would not keep growing the current ad hoc list resource model. I’d do this:

1. Define a proper `ResourceAlgebra` / PCM interface:
```lean
class ResourceAlgebra (R : Type) where
  unit : R
  comp : R → R → Option R
  valid : R → Prop
  -- unit, commutativity, associativity, validity, compatibility laws
```

2. Define assertions generically:
```lean
abbrev Assertion (S R : Type) := S → R → Prop
```

3. Instantiate pointwise `CompleteLattice` / `CompleteBooleanAlgebra` for assertions, so Loom can use them.

4. Define CSL operations separately:
```lean
emp
sep
wand
owns
persistent/pure facts
```

5. Be careful about pure facts. Loom’s `⌜p⌝` means “if `p`, then top; otherwise bottom.” That is persistent and consumes no ownership. Current CLean’s `CSL.pure` means `p ∧ emp`, which consumes exactly empty resource. Those are different. We should probably keep both, with clearer names.

6. Define PTX primitive specs as Loom `WPGen`s whose generated preconditions are CSL assertions.

7. Prove frame rules and scheduler preservation from the PCM laws.

So the answer is: Loom gives us the right generalized Dijkstra/VCGen substrate, but not the PTX CSL. We need to build the CSL/PCM layer ourselves, then either plug it into Loom or fork a Loom-inspired subset if dependency/toolchain friction gets too high. Mathematically, the clean target is **Loom-style monadic WP over a BI/separation-logic assertion lattice backed by a PTX resource algebra**.

**1. Annotated Program, Separate From Source**
Systems often keep the original program immutable, but build a separate “decorated” or “annotated” version for proof:

```lean
def prog : Program := ...

def proofHints : AnnotationSet := {
  loop "outer.header" := outerInv,
  loop "inner.header" := innerInv,

}
```

The invariants are not part of the executable PTX. They are proof metadata. The final theorem only mentions `prog`, `pre`, and `post`; the proof uses `proofHints`.

This is probably the best CLean direction.

**2. Invariants Keyed By Source/CFG Locations**
For low-level code, extrinsic verifiers usually index invariants by program points:

```lean
loopInvariant "L_outer" outerInv
loopInvariant "L_inner" innerInv
```

Nested loops are not special mathematically. They just have different headers:

```text
outer_header:
  ...
  inner_header:
    ...
    br inner_header
  ...
  br outer_header
```

Then:

```lean
annotations :=
  .loop "outer_header" outerInv
  .loop "inner_header" innerInv
```

The inner invariant can mention the outer loop variables. The proof obligation for entering the inner loop is:

```text
outer invariant + setup before inner loop ⊢ inner invariant
```

The proof obligation for exiting the inner loop is:

```text
inner invariant + exit condition ⊢ state needed by the rest of outer body
```

So nested loops compose through ordinary entailments.

**3. Structured Loop IDs**
If the frontend can reconstruct structured loops, it can assign stable loop IDs:

```lean
.loop 0 outerInv
.loop 1 innerInv
```

or better:

```lean
.loop "outer_k_loop" outerInv
.loop "inner_tile_loop" innerInv
```

This is nicer than raw block labels, but it requires CFG analysis. For PTX, I’d avoid relying only on this because optimized/lowered PTX may be less structured.

**4. Cutpoint Invariants**
For unstructured CFGs, classical Floyd/Hoare verification uses **cutpoints**. A cutpoint is a program location where we summarize potentially cyclic control flow.

For reducible CFGs, loop headers are enough. For irreducible CFGs, you may need extra cutpoints.

So instead of requiring invariants for every block:

```lean
BlockLabel → Assertion
```

we should require a sparse map:

```lean
CutpointMap : BlockLabel → Option Assertion
```

Then VCGen computes straight-line WPs between cutpoints. This is much better:

```text
cutpoint L_outer_header: outerInv
cutpoint L_inner_header: innerInv
cutpoint exit: post
```

Blocks without annotations are handled by WP expansion.

**What I’d Want For CLean**
User-facing proof should look closer to:

```lean
def saxpyPTX : KernelEnv := ...

def saxpyAnn : PTXAnnotations where
  loops := [
    { header := "loop", invariant := saxpyLoopInv }
  ]

theorem saxpy_correct :
  PTXPartialCorrect saxpyPTX saxpyPre saxpyPost := by
  apply verify_ptx saxpyAnn
  ptx_vcgen
```

For nested loops:

```lean
def matmulAnn : PTXAnnotations where
  loops := [
    { header := "row_loop", invariant := rowInv },
    { header := "col_loop", invariant := colInv },
    { header := "k_loop",   invariant := kInv }
  ]
```

The invariants are external proof annotations, not source annotations and not theorem assumptions.

**Mathematically**
The clean model is Floyd-style verification:

- Associate assertions with selected cutpoints.
- For every path from one cutpoint to the next, compute WP backwards.
- Generate a VC saying the source cutpoint invariant implies that path WP.
- For backedges, this becomes invariant preservation.
- For exits, invariant plus exit condition implies postcondition.

So the raw internal representation may still be:

```lean

```

or sparse equivalent, but the user should interact with:

```lean

```

That scales to nested loops because each loop header is a distinct program point. The outer invariant does not “contain” the inner invariant globally; it only has to establish it when control enters the inner loop.

```lean
ptx_loop "outer" with outerInv
· ...
```

```lean
abbrev Assertion := State → Resource → Prop

wp (stepInstr cta warp gi) post :=

    ∀ st',
      Helpers.stepInstr? st cta warp gi = some st' →
        ∃ r',
          Resource.Update r r' ∧
          post () st' r'
```

For the scheduler:

```lean
wp machineStep post :=
  fun st r =>
    ∀ cta warp st',
      StepWarp st cta warp st' →
        ∃ r',
          Resource.Update r r' ∧
          post () st' r'
```

That is the core PTX predicate transformer. Then sequencing is still monadic:

```lean
wp (x >>= f) post =

```

**What `DivM` Does**


For partial correctness:


because nontermination is allowed.

For total correctness:

```lean
wp div Q = False
```

because nontermination violates total correctness.

That interpretation is given by Loom’s `MAlgOrdered DivM Prop` instances.

**What `NonDetT` Does**
`NonDetT` is Loom’s nondeterminism/loop transformer. It has constructors like:


Under demonic verification, nondeterministic choice means universal choice:

```lean

```

Under angelic verification, it means existential choice:

```lean
wp (pick x satisfying p) Q = ∃ x, p x ∧ Q x
```

Loops are represented by `repeatCont`, and the WP rule quantifies over/proves an invariant. The user-written `while ... invariant ...` syntax is macro-expanded into a `for _ in Lean.Loop.mk` with `invariantGadget` calls. Those gadgets are runtime no-ops, but the VC generator sees them.

**How VCGen Works**
Loom defines:

```lean
wp c post := liftM c post
```

A `WPGen c` is a certificate:

```lean

  get  : Cont l α
  prop : ∀ post, get post ≤ wp c post
```

So VCGen computes a symbolic precondition `get post`, then proves it sound against the real semantic `wp`.

The `wpgen` tactic unfolds the Velvet method, sees a monadic Lean term, and recursively applies registered `WPGen` rules:


ASSISTANT:
Yes. Velvet gets away with ordinary Lean state/semantics because its programs are already Lean monadic terms. PTX cannot do that, because PTX is external code with explicit machine state. That is exactly why our backend needs a custom PTX monad/algebra.

**Why CSL, Not Velvet Logic**
Velvet mostly verifies structured Lean programs over Lean values:

```lean
pre  : Prop
post : α → Prop
```

or, for stateful effects, ordinary predicates over threaded values. Mutation is value-threaded by Lean elaboration. There is no low-level aliasing model, no global/shared/local memory ownership, no warp scheduler, no per-lane register ownership, no barrier tokens.

PTX needs CSL because we need to reason locally about pieces of a concurrent machine:

```lean
reg cta warp lane "%r1" v
∗ pred cta warp lane "%p" b
∗ globalByte addr .write x
∗ sharedByte cta off .write y
∗ warpAt cta warp pc lanes
```

The PCM/resource algebra tells us when those pieces can coexist. That gives the frame rule:

```text
{P} instr {Q}
-----------------------
{P ∗ R} instr {Q ∗ R}
```

provided `R` is stable under the instruction. Velvet does not need this kind of ownership accounting; PTX does.

**The Shape I’d Use**
I would split the PTX monad into two layers:

```lean
PtxBase  -- primitive PTX effects with custom CSL WP
PtxM     -- Loom nondeterminism/choice layer over PtxBase
```

Sketch:

```lean
abbrev PtxAssertion := State → CSL.Resource → Prop

inductive PtxOp : Type → Type where
  | getState : PtxOp State
  | instr : CTAId → WarpId → GInstr → PtxOp Unit
  | terminator : CTAId → WarpId → Terminator → PtxOp Unit
  | warpStep : CTAId → WarpId → PtxOp Unit
```

Then a free monad over those ops:

```lean
inductive PtxBase (α : Type) where
  | pure : α → PtxBase α
  | vis : {β : Type} → PtxOp β → (β → PtxBase α) → PtxBase α
```

with normal `pure`/`bind`.

The primitive WP is the important part:

```lean
def wpOp : PtxOp α → (α → PtxAssertion) → PtxAssertion
  | .getState, Q =>
      fun st r => Q st st r

  | .instr cta warp gi, Q =>
      fun st r =>
        ∀ st',
          Helpers.stepInstr? st cta warp gi = some st' →
            ∃ r',
              CSL.Resource.Update r r' ∧
              Q () st' r'

  | .terminator cta warp term, Q =>
      fun st r =>
        ∀ st',
          Helpers.stepTerminator? st cta warp term = some st' →
            ∃ r',
              CSL.Resource.Update r r' ∧
              Q () st' r'

  | .warpStep cta warp, Q =>
      fun st r =>
        ∀ st',
          StepWarp st cta warp st' →
            ∃ r',
              CSL.Resource.Update r r' ∧
              Q () st' r'
```

Then define the monadic WP structurally:

```lean
def PtxBase.wp : PtxBase α → (α → PtxAssertion) → PtxAssertion
  | .pure a, Q => Q a
  | .vis op k, Q => wpOp op (fun x => PtxBase.wp (k x) Q)
```

This gives the Dijkstra bind law by construction:

```lean
wp (x >>= f) Q = wp x (fun a => wp (f a) Q)
```

Then instantiate Loom:

```lean
instance : MAlgOrdered PtxBase PtxAssertion where
  μ c := PtxBase.wp c id
  ...
```

After that, use Loom’s `NonDetT` for nondeterminism:

```lean
abbrev PtxM α := NonDetT PtxBase α
```

In demonic partial-correctness mode, `pickSuchThat` becomes universal choice. That is exactly what we want for scheduler nondeterminism.

**Machine Step**
Using `NonDetT`, scheduler choice can be written monadically:

```lean
def execWarpStep (cta : CTAId) (warp : WarpId) : PtxM Unit :=
  liftM (PtxBase.vis (.warpStep cta warp) PtxBase.pure)

def machineStep : PtxM Unit := do
  let st ← liftM (PtxBase.vis .getState PtxBase.pure)
  let cw ← pickSuchThat (CTAId × WarpId)
    (fun cw => ∃ st', StepWarp st cw.1 cw.2 st')
  execWarpStep cw.1 cw.2
```

Under demonic WP, this simplifies morally to:

```lean
fun st r =>
  ∀ cta warp,
    (∃ st', StepWarp st cta warp st') →
      ∀ st',
        StepWarp st cta warp st' →
          ∃ r',
            Resource.Update r r' ∧ post () st' r'
```

That is the robust replacement for the single-warp assumption. The invariant must be preserved by every runnable warp.

**Why Not Plain `StateT State`**
A tempting design is:

```lean
StateT State (NonDetT DivM)
```

But that only gives predicates over machine state. It does not explain resource ownership or framing.

Another tempting design is:

```lean
StateT (State × Resource) ...
```

but that treats the ghost resource as ordinary global state. That is bad for separation logic: an instruction should update only the local owned footprint and leave framed resources untouched. The current WP shape:

```lean
∃ r', Resource.Update r r' ∧ post st' r'
```

is local and frame-friendly. A global ghost-state update is the wrong abstraction.

So the resource should live in the assertion semantics, not in the executable machine state.
